The fourth release of stafeto runs on AWS: the system boots on an EC2 Graviton instance (t4g) through an EFI loader, takes its address by DHCP over the ENA network device, and fetches pages with `wget` and `curl`. It also closes holes in how set-ID programs take their sessions, seeds the entropy service at boot, builds all C code with the stack protector, and fixes defects found in the lock service of the RAM file service and in its handling of departing clients. The kernel is still a small capability microkernel in Rust for AArch64; it boots in QEMU (`virt`) on any host, with HVF acceleration on a Mac with Apple silicon, under Apple Virtualization.framework, and now on EC2.

## Try it

Download `stafeto-0.4.0-aarch64-virt-base.tar.xz` (the shell, the package tool and the base packages) or `stafeto-0.4.0-aarch64-virt-full.tar.xz` (every package, including the network programs; it needs 1024M of memory), unpack it and run `./run.sh` (`--cpus 4` for four CPUs, `--hvf` on a Mac with Apple silicon).

## Try it on AWS

AMI: (filled in at publication)

Launch a `t4g.small` instance from the public AMI in `eu-central-1`. The AMI boots in UEFI mode and needs the ENA network device, which every t4g instance has. Give the instance a security group and read the console with the EC2 serial console or the system log: the lines `ena: link up` and `net: lease <address>` show that the network is up.

To register an AMI yourself, use the attached disk image `stafeto-0.4.0-aws-disk.raw.xz`. Unpack it with `xz -d`; the result is a raw disk with a GPT, an EFI system partition and the loader, the kernel and the boot image. Put it into an EBS snapshot (the EBS direct API, or `aws ec2 import-snapshot` with the format `RAW`) and register the snapshot as the root volume of an image with the same settings the tree's `cargo xtask aws image` uses:

    aws ec2 register-image --name stafeto-0.4.0 --architecture arm64 \
      --virtualization-type hvm --boot-mode uefi --ena-support --imds-support v2.0 \
      --root-device-name /dev/sda1 \
      --block-device-mappings DeviceName=/dev/sda1,Ebs={SnapshotId=<snapshot>,VolumeType=gp3,DeleteOnTermination=true}

With a checkout of the source and the AWS profile `stafeto`, `cargo xtask aws image --disk stafeto-0.4.0-aws-disk.raw` makes the snapshot and registers the image in one command.

## Highlights

- **AWS EC2 Graviton (t4g).** An EFI loader reads the ACPI tables of the instance and gives the kernel a device tree, the system boots from a GPT disk with an ESP, and the console is a 16550 serial port that the SPCR table names. The kernel's ITS tables sit on 64 KiB blocks, which the virtual ITS of EC2 requires; every register of the ITS is read back and a delivery self-test runs at every boot, and a lost interrupt turns MSI off with a line on the console. `lib/pci` enumerates the PCI buses through ECAM and measures the BARs. The ENA driver (`lib/ena`) brings the device up over one queue pair with MSI-X vectors, and `netd` runs its stack over it: DHCP, answers to ping, `wget` and `curl` work on EC2 (pull requests #323, #326, #329).
- **Boot seed.** The EFI loader reads `EFI_RNG_PROTOCOL` (and the SMCCC TRNG and `RNDR` where the machine has them) before it leaves the firmware and mixes the result into `/chosen/rng-seed`. The kernel hands the seed to `init` in one page and clears it in the device tree, and the entropy service starts from it, so an EC2 instance, which has no random device, does not use a weak key (#332).
- **Set-ID programs.** A set-ID program takes its Pipes, Net and Entropy sessions only when the service that owns the slot vouches for them; any other channel is replaced by a new session with no descriptions. A set-ID program no longer takes the Entropy session from its caller (#324, #328, #331).
- **Shared memory waits.** A wait on an address in shared memory needs the right to the object, and the level of the waiter comes from the process record; a process that holds no object can no longer take the wake of a semaphore or mutex that belongs to another user (#325).
- **Stack protector.** The loader gives the stack canary its value from `AT_RANDOM`, and all C code that runs in the guest (BusyBox, bash, nano, htop, ncdu, ncurses, curl, OpenSSL, nginx, F-Stack, Doom and the probes) is built with `-fstack-protector-strong`: an overflow in a protected function ends the program with `SIGABRT` and the line `stack smashing detected`. `crypt` takes its salts from `getrandom`, and `mkstemp`, `tmpnam`, the DNS transaction number and similar draws fail with `ENOSYS` without entropy and use no clock (#333, #334, #336).
- **Reliability.** The lock maintenance of the RAM file service charges every tick it runs, which ends a stall of a sleeping client behind it (#327). Every own step of the service stays under 16,500 ticks under `-icount`, with the sweep of dead locks bounded per turn (#330, #335). A closed label that departs beside a running session departure no longer leaves a birth slot behind (#336).
- **Packages.** The release key `stafeto-release-2026` has its certificate in `keys/`, and the packages of a release are listed in an index signed with it (#339). The series 0.4 is frozen in `packages/abi.txt`.

## Limits

- The ENA driver uses one queue pair, and the Low Latency Queue mode is not implemented. The consumers of the network switch (`nginx-fast`) are refused on ENA.
- Only one instance type, `t4g.small`, is tested.
- Only the region `eu-central-1` is tested, and the public AMI is there.
- The network is IPv4. `wget` checks no certificate and speaks TLS 1.2 only.
- The file system lives in RAM unless a disk is attached; changes are gone after a restart.
- Graphics is a preview with one full-screen program, and there is no sound yet.
- Nine POSIX utilities wait for services of their own: `at`, `batch`, `lp`, `mailx`, `locale`, `localedef`, `gettext`, `ngettext` and `msgfmt`.
- Interfaces may still change inside 0.x. The series 0.4 is frozen in `packages/abi.txt`: a package built for it runs on every system of the series.
