The release 0.6.0 of stafeto connects POSIX programs to the data volume and starts the graphics stack of the composition service. A POSIX program now sees `/data`, the volume that keeps its files across reboots, with permissions by the rules of POSIX. The composition service has a frame clock, opens the screen in small steps, and draws the elements of an OpenWF Composition scene; a C program can drive the display driver through OpenWF Display. The release opens no new part of the system beyond these and freezes the ABI of the series 0.6. The kernel is still a small capability microkernel in Rust for AArch64; it boots in QEMU (`virt`) on any host, with HVF acceleration on a Mac with Apple silicon, under Apple Virtualization.framework, and on AWS EC2 Graviton.

## Try it

Download `stafeto-0.6.0-aarch64-virt-base.tar.xz` (the shell, the package tool and the base packages) or `stafeto-0.6.0-aarch64-virt-full.tar.xz` (every package, including the network programs; it needs 1024M of memory), unpack it and run `./run.sh` (`--cpus 4` for four CPUs, `--hvf` on a Mac with Apple silicon).

## Try it on AWS

The public AWS image of 0.6.0 replaces the image of 0.5.2. It has the contents, launch steps and limits described in the notes of 0.5.1 (`docs/releases/0.5.1.md`), with the data volume now served to POSIX programs as `/data` and with nginx and nginx-fast 1.30.7. AMI: `ami-04d65173ce457da3c` in `eu-central-1` (public, name `stafeto-0.6.0`, arm64, UEFI). It was checked on a t4g.small: `uname -r` 0.6.0, the clock from the firmware, the data volume with a file written and read under `/data`, nginx 1.30.7 on 80 and 443, nginx-fast on 8080, SSH with the key pair of the instance, a launch with the data volume left out, and `pkg update` at the index of the series 0.6, serial 1. The image of 0.5.2 is no longer public.

## What the release brings

### POSIX programs on the data volume

The data file service (`datafs`, littlefs on the data disk) serves `/data` to every POSIX program. `docs/data.md` says what a program gets and `docs/posix-coverage.md` lists the departures from POSIX.

- **Calls.** `open`, `read`, `pread`, `write`, `pwrite`, `lseek`, `stat` and `fstat`, `access`, `opendir` and `readdir`, `chdir` (a directory under `/data` can be the current directory), the `*at` calls, `ftruncate`, `fsync`, `mkdir`, `rmdir`, `unlink`, `rename`, `chmod`, `chown`, `utimensat` and `O_APPEND`. `mmap` of a file for reading works as a private mapping. Descriptions of `/data` survive `fork`, `posix_spawn` and `exec` and travel through a Unix socket with SCM_RIGHTS.
- **Rights and attributes.** The service asks the process service who the caller is and applies the rules of POSIX (the same code as the RAM file service): search on each directory of a path, read and write by the mode, ownership for `chmod`, `chown` and `utimensat`, the umask, the sticky directory. A description keeps the rights it was opened with over `chmod`, `setuid`, `fork`, `exec` and a pass through a socket.
- **Durability.** Names (`mkdir`, `rmdir`, `unlink`, `rename`, `chmod`, `chown`, `utimensat`) are durable when the call returns. File data is durable at `fsync`, at the close of the last description and when the service needs the room. A file written to a temporary name, synced and renamed over the old one leaves one whole generation after a power cut.
- **Limits.** A volume holds up to 2,048 metadata pairs and 1,024 directories, and a directory up to 1,024 entries; beyond that creation answers ENOSPC, and removal always works. Every file takes at least 4 KiB. About 20,000 to 30,000 files with names up to 32 bytes fit (about 6,000 with names of 255 bytes).
- **Volume format 4 and the conversion of a 0.5 volume.** The version 0.6 marks the volume with format 4. A volume of 0.5 is converted at the first mount by 0.6: after the service says READY a job walks the volume one entry at a time, keeps the file numbers, moves a file that an older build kept inline to a block of its own at its first open for writing, and gives every entry the attributes of an owner and a mode. Until an entry has had its turn it shows root, group 0 and mode 0600 (0700 for a directory). A volume that 0.6 has converted is not converted back, and the services of 0.5.x do not know its owners and modes.
- **BusyBox `vi`.** The shell image has `/bin/vi`. It edits and saves a file on `/data` (it writes in place with `open`, `write`, `ftruncate` and `close`), and the probe `vi-dialog` types a file, saves it, reads it back, edits it again and reads it after a second boot of the same disk.
- **Open POSIX on `/data`.** `open-posix --data` runs the file-related tests of the Open POSIX Test Suite with their scratch files on the volume: 92 of 111 pass. The 19 that fail map a file shared, and `MAP_SHARED` of a file of `/data` is ENODEV by design.
- **Probes.** `data-posix` (the read, write, restart and crash probes of the layer), `data-save` (a file saved the way `sed -i` saves it, read back after a reboot) and `vi-dialog` run in `ci`.

### Graphics

- **The frame clock.** The composition service starts its frames at the periods of a clock, 60 Hz by default. The period and the cap can be set. A period holds at most 47 bands, which is 0.75 of the period divided by the band gate of 16,328 ticks, so the service takes about 79 % of a period and leaves the rest to the levels below it. The request SET gives a window an interval (its buffer is taken at most once in N periods, with late and missed frames counted), and STATS answers 17 counters, a histogram of the frame time in 33 buckets and a record for each window. `docs/compositor.md` defines each counter.
- **The late opening of the screen.** When the screen opens from a request, the service maps the frame buffer in portions of 32 pages and then takes one step each for SUBSCRIBE, PIPELINES, the cursor and the pool source. Requests that need the screen are answered CLEARING meanwhile, and the frame clock takes no frame before the last step. Under `-icount` the longest mapping step is 7,535 ticks and the longest finishing step 12,790, both under the gate of 16,328 (`cargo xtask comp-late-probe`).
- **OpenWF Display.** `lib/wfd` implements the rules of an OpenWF Display 1.0 device over the display driver (`proto_gpu` revision 3): handles, attributes, the cached configuration, commits that become one LAYERS request, and event queues. The feature `wfd` of the POSIX layer gives a C program the functions of `wfd.h` (the Khronos header, unedited, with `wfdext.h` and two extensions of stafeto). The demo `wfd-demo` binds the compositing target and the pool buffer to the primary pipeline in turn and moves a cursor picture, and `cargo xtask wfd-probe` checks 100 frames against the guest's CRC, a host-computed CRC and the screenshot of QEMU. `libc.so` is built without the feature, so the ABI fingerprint does not change.
- **The scene session of OpenWF Composition.** The composition service keeps a pending and a working scene. The requests SCENE_COMMIT (26) and SCENE_COMPOSE (27) carry up to 16 elements of 56 bytes in a message, a commit is atomic, a window that no element shows gets its buffer back, and the channel has the bits COMMITTED and COMPOSED. The window format A8 holds masks.
- **The drawing of scene elements.** The service draws every element of a scene through pixman: the stretch, turns by quarters, the reflection, the nearest and bilinear filters, the global alpha, the window's own alpha and the A8 mask. A reference in `proto_comp` works out each point from the geometry of the element, and `comp-probe` shows six scenes whose screenshots equal the reference's CRC. A scene whose layers do not fit one step is drawn in groups of layers, a step each, so no scene is refused. The band price table has a row for each operation, fitted to measured shapes.
- **Not in this release.** The client library of OpenWF Composition (libWFC, `wfc.h`) is not part of it.
- **Also in this release.** The display protocol `proto_gpu` revision 3 (PIPELINES, SOURCE and LAYERS) with a cursor queue in the Virtio GPU driver, the window library for C programs (`<stafeto/window.h>`), pixman with its AArch64 NEON paths, and the LVGL demo `lvgl-demo` with FreeType text.

### Packages

- **nginx 1.30.7.** The packages `nginx` and `nginx-fast` are version 1.30.7, as in 0.5.2.
- **Updates of packages alone.** A tag `v<series>-pkgs.<k>` starts a run of the signing pipeline with no new version of the system: it raises the serial of the index of the series and publishes the changed packages (`docs/release.md`, "Packages-only updates").
- **Carry by content.** When the recipe of a package differs from the published entry and the version is the same, the package is carried if its manifest and its metadata equal those of the published file.
- **Reproducible builds.** The scripts that build packages run with `SOURCE_DATE_EPOCH` and `PYTHONHASHSEED` fixed, and `cargo xtask pkg-repro` builds every package twice from an empty `target/` and compares the results. On GitHub it found 23 packages and no difference. Both builds run in the same checkout path, so paths of the build tree inside programs are not covered.
- **New packages.** `freetype` 2.14.3 and `lvgl` 9.6.0 (with the program `lvgl-demo`) are packages of the games image. `busybox` links `/bin/vi`.

### Kernel and services

- **The log wake of the console driver.** The kernel posts one notification through the line `LOG_LINE` when a record lands in a ring the console driver has not taken. An idle system wakes the driver 10 times in 10 s for its log work where it woke 500 times, with no budget overrun under `-icount`. The driver keeps a safety tick once a second that reports a missed wake.
- **The thread place query.** `object_info` has a diagnostic kind THREAD_PLACE (20) for the holder of the system resource. It tells the CPU of a thread, where the thread stands, its command flags and the state of the CPU it runs on. `init` prints the place of a silent service's thread in its `silent service` line. Each path of the null call gains 4 instructions, so `NULL_MAX` goes from 271 to 275.
- **Parked lock pages in the RAM file service.** One unlock of a whole file or one close that emptied 64 lock records released 64 pages in a single step, 21,157 and 21,444 ticks against the term B of 20,410. A request now parks the page it empties, and a maintenance turn releases 16 pages at a time.
- **The step gate.** A step is judged by two charges for each preemption it counts: 487 ticks against the hard bound B (20,410) and 1,300 ticks against 0.9 B (18,369). The step statistics of `lib/rt` keep the longest step for each count of preemptions.
- **The stack of `pkgd`.** The loop of the package service had a frame of 19,216 bytes in a stack of 32 KiB, and the nudge of the watchdog overran it (a data abort at the end of the stack). The table of sessions is now built in place and the frame is 12,704 bytes.

## Limits

- `/data` is slow: a call moves 1 KiB at most (1,012 bytes of a write, 1,004 of a pwrite), so a large file is thousands of calls. Under QEMU 64 MiB were written in 31 s and read in 48 s; 8 MiB took 8,290 write calls and 11.4 s. A write of more than one message can have another process's bytes between its messages, and a reader of a file rewritten in place can see old and new bytes in one read. The fix (a transfer through a memory object) is planned after 0.6.
- A shared mapping of a file of `/data` is ENODEV. Record locks are ENOLCK. A program is never run from `/data` (EACCES). The volume has no links (`link` of a file is EMLINK, `symlink` EPERM, `rename` across file systems EXDEV), `unlink` of a directory is EISDIR, and `a/ghost/..` under `/data` is read as text and names `a`.
- Reads never update `atime`: the volume behaves as if mounted `noatime`.
- Removing a tree of a thousand directories takes about 18 minutes on EBS gp3 (3.3 million reads at 3,000 reads a second), and one removal takes up to about 2 s.
- The first call under `/data` after a boot can wait for the first walk of the volume (up to about a minute on a full 2 GiB volume on EBS gp3). An image with no data service answers EIO after a second for a path under `/data`.
- A process holds at most 32 open descriptions of `/data`, a process tree has 8 requests in flight, and everyone logged in through `sshd` shares one tree.
- The composition service draws on the CPU only. Under a scene each element layer pays for the lookup in the path cache of pixman, which has 8 places, so a scene evicts it every band.
- The limits of 0.5.1 that the list above does not change still apply, and the system is experimental.

## Compatibility

The ABI of the series 0.6 is frozen: `cargo xtask abi --check` reports `series 0.6 frozen, no change`, and the packages of 0.6.0 run on every 0.6.x. The change from 0.5 to 0.6 moves two of the four parts of the fingerprint in `packages/abi.txt`. The part `libc` (the names `libc.so` exports) and the part `layouts` (the layouts and constants of the headers) are the same as in 0.5. The parts `loader` and `protocols` changed.

- **Loader.** The start area has a slot `Data` (14, the session with the data file service) and a descriptor name for a description of the volume; the version of the loader is 7 (6 in 0.5) and the start area is 10.
- **`proto_process` version 16.** TakeRoot (method 44) gives a process the root of the data service.
- **`proto_pipe` version 4.** A word of kinds after the count of descriptions lets a description of `/data` travel in SCM_RIGHTS.
- **`proto_data` version 3.** The layer speaks the protocol of the data service.

A package belongs to the series it was built for, and the promise of a series covers the packages of that series. A program built for 0.5 links against the same names and layouts of `libc.so`, but no test runs 0.5 packages on 0.6 and the loader and the protocols differ, so rebuild programs for 0.6. The packages of the series 0.6 come from the index at `https://stafeto.github.io/packages/0.6/aarch64`.

A data volume of 0.5 is converted at its first mount by 0.6 (see "POSIX programs on the data volume") and is then marked with format 4. The data service of 0.5.2 reads no format mark and does not recognize a format 4 volume, so do not attach a volume that 0.6 has converted to a system of the series 0.5.

For people who build images: the data volume is served to POSIX programs when the image has the data file service, whose table entry also gives it a budget for its worker thread (3 ms of each 10 ms on CPU 1). `cargo xtask data-image` makes the volume file as in 0.5.1.
