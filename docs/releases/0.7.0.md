This file collects the lines of the notes of 0.7.0 as the parts that make the release land. The other parts add their own sections before the release is tagged.

## What the release brings

### Fast large calls on /data

- **Calls of any size.** A `read`, `write`, `pread` or `pwrite` on `/data` of more than one message goes in parts of up to 64 KiB through a window of 128 KiB that the process registers with the data service, under a lease on the file. The call is atomic against other callers: another process sees the file before it or after it. The end of an O_APPEND description is taken once for the call. `docs/data.md` has the rules.
- **Speed.** Under QEMU, 64 MiB are written in 3.3 s and read in about 4.1 s on a Mac with Apple silicon, and written in 8.7 s and read in about 10.7 s on the GitHub runners. A written block costs 1.5 disk operations and a read block 2.0. Two optional changes of the vendored littlefs bring this: wayposts into the list of blocks of a file (`ctz_hints`) and no read back of a block that the disk reported written (`trust_prog`).
- **Leases lapse.** A lease ends 1 s after the answer to a part with no next one, and when others wait for the file once the client's time between parts passes 1 s in all. The late part is not run and the program gets a short `write()` or `read()` with the bytes done.
- **Signals.** The entry of a signal handler is deferred from the send of a part until its lease is on record, so a handler that jumps out with `siglongjmp` releases the lease at once.
- **`proto_data` version 4.** The methods WINDOW, READ_INTO, PREAD_INTO, WRITE_FROM, PWRITE_FROM, RELEASE, OPEN_NUMBERED and MKDIR_NUMBERED and the status NO_WINDOW. The series 0.7 is open, so the fingerprint of its ABI records them.
- **Probes.** `data-fast`, `data-atomic` and `data-steps` run in `ci`, and `datafs-breaks` checks that the deliberate breakages of the lease, the wayposts and `trust_prog` each fail their tests.

### Layered root: copy up of lower files

- **`proto_fs` 23, names.** A request that would write a file of the lower set (an open for writing, `truncate`, `chmod`, `chown`, `utimensat`) is answered COPYING with a ticket, and the program asks WAIT with the ticket. WAIT takes an optional handle (a copy of the caller's channel, NOTIFY, labelled with the ticket and bit 62) and is answered at once: 0 when the copy is over, the failure of the copy, or COPYING while it goes on; with a handle the service keeps the notification (16 in all, 4 for a session) and notifies it when the copy ends, so a signal can end the wait in `receive`. A ticket with a bit above its place and generation is INVALID_ARGUMENT. The methods and the numbers are those of the open series; the fingerprint of the ABI does not move.
- **Behaviour.** The first write of a lower file takes as long as its copy (about 8 MiB/s on gp3), a program of the lower set (first bytes `\x7fELF`) is never copied (EROFS), and the copy keeps the number, owner, mode and times of the lower file. See `docs/posix-coverage.md`, item 10 of the layered root.

### Layered root: switching on the layer client

- **Every POSIX program has the layer client.** `libc.so` and the static library of the packages are built with the feature `layer` (`tools/layer-features.txt`). The program has the symbol `stafeto_layer_client`, and the fingerprint of the ABI records the feature and the symbol (the series 0.7 is open). The root of an image is layered only when init is built with the feature `layered-root`, which stays off by default: the measurement on AWS (293 s from the READY of the data service to that of the layer service for 8,192 names) is far over the plan's limit, and the fast build of the index (issue 657) comes first.
- **`proto_process` 19: ABSENT.** TakeRoot for a root whose service the table of init does not have answers ABSENT at once (the list `roots=` in the process service's own arguments, built from the table). A program of an image with no layer service takes the file service's answers from its first path, with no wait.
- **`proto_fs` 23: GUARD.** A one-way request of the boot profile (method 86): the RAM file service of a layered root refuses a POSIX session's writes outside the pass-through names only after it. The layer service sends it after its READY; with no data volume it sends nothing, answers every SESSION with NO_STORE, and the root writes to memory.
- **Scripts.** A script that starts with `#!` in a layer of the user runs through its interpreter (`execve`, `posix_spawn`); the interpreter is checked as every program is.
- **Waits.** A record of init's table waits for three services at most; the launcher of the layered shell waits for the layer service, the host key service and the package service. The launcher's wait for the layer service, init's watch of its start and the program's wait for STARTING are a minute, temporary until the fast build of the index.
- **Lines.** The layer service says at READY how many calls it made to the data file service and how long it waited for them, and its longest step of the build by the clock; the NVMe service says when its budget is overrun.

### Limits

- On an EBS gp3 volume without added IOPS (3,000 operations a second) each block of 4 KiB is one operation, so the write is bound at about 8 MiB/s and the read at about 5.9 MiB/s. The measurement on AWS is not in these notes yet.
- A job that waits for a file under a lease waits as long as the holder's call lasts, up to a lapse; a write of 64 MiB holds the readers of its file back for about 3.3 s of the service's work on a Mac (8.7 s on the runners).
- `readv` and `writev` of a program on `/data` still go one buffer at a time (issue #581).
