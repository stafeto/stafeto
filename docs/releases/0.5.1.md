> The public AWS image of 0.5.1 was withdrawn on 2026-11-20: its nginx 1.30.6 has nine security issues fixed in 0.5.2. Use the image of 0.5.2, `ami-09b3283d1b189c12b`, described in the notes of 0.5.2.

The release 0.5.1 of stafeto is the try-out release for AWS. It brings a public image for EC2 Graviton with SSH, nginx on 80 and 443, `nginx-fast` on 8080 and the package tool, a persistent data volume that keeps the SSH host key, and the fixes that running on a real `t4g.small` showed to be needed: the clock, the accept queue of the network service, the watchdog of `init` and a few smaller defects. The service budgets of 0.5.0 stay as they are and gain parts that remove two defects. The kernel is still a small capability microkernel in Rust for AArch64; it boots in QEMU (`virt`) on any host, with HVF acceleration on a Mac with Apple silicon, under Apple Virtualization.framework, and on AWS EC2 Graviton.

## Try it

Download `stafeto-0.5.1-aarch64-virt-base.tar.xz` (the shell, the package tool and the base packages) or `stafeto-0.5.1-aarch64-virt-full.tar.xz` (every package, including the network programs; it needs 1024M of memory), unpack it and run `./run.sh` (`--cpus 4` for four CPUs, `--hvf` on a Mac with Apple silicon).

## Try it on AWS

AMI: `ami-03056ca4250852532` in `eu-central-1` (public, name `stafeto-0.5.1`, arm64, UEFI)

The image is experimental. Read the warning on its landing page: keep no secrets on the instance and open its security group to your own address only.

What the image holds:

- **nginx** on ports 80 and 443 (2 workers, TLS 1.3, HTTP/2). The certificate is a self-signed EC P-256 certificate that the instance makes at every boot; the key is made there and is in no file of the image. Use `curl -k`.
- **nginx-fast** on port 8080, which runs on the user-space FreeBSD stack (F-Stack) through the network switch of `netd` over the ENA device.
- **Dropbear** SSH on port 22. The boot script reads the public key of the key pair of the instance from the instance metadata (IMDSv2 only) and logs in `root` with it. An instance launched with no key pair has no SSH.
- **pkg** with the index of the series 0.5 from `https://stafeto.github.io/packages/0.5/aarch64`: `pkg update`, `pkg search`, `pkg install htop` work on the instance. The package store lives in memory (256 MiB), so installed packages are gone after a reboot.
- **A landing page** on all three web ports: what stafeto is, that it is experimental, how to log in, what to try, what is lost at a reboot and the warning about secrets and the security group.

To launch it:

1. Use the region `eu-central-1` and the instance type `t4g.small` (the only type tested). The image boots in UEFI mode and needs the ENA network device, which every t4g instance has.
2. Give the instance a key pair and a public IPv4 address.
3. Use a security group whose inbound rules allow TCP 22, 80, 443 and 8080 from your own address (a /32) and nothing else.
4. Log in with `ssh root@ADDRESS` and the private key of the pair, or open `http://ADDRESS/`.
5. Read the console with the EC2 system log: the lines `ena: link up`, `net: lease <address>`, `web: nginx on 80 and 443`, `fast: nginx-fast on 8080` and `ssh: host key SHA256:...` show that the services are up, and the SSH fingerprint on the console is the one to compare at the first login.

`htop` needs `TERM=vt100` (the image has no terminfo for other terminals).

### What was measured on a t4g.small

These are measurements of single runs in `eu-central-1`, from a machine on the public internet, so the times include the network path to the instance (about 28 ms of delay to the instance).

- **Boot.** The console line `fast: nginx-fast on 8080`, which ends the boot script, appeared 189 s and 190 s after the launch request in the two runs that measured it before the data volume, and 46 s and 39 s (the second without the data volume) in the later runs. The times include the poll of the console by the tool and the delay of the EC2 console output; the difference between the earlier and the later runs was not investigated.
- **Requests.** A loop of one request after another to the three ports for nine to ten minutes: 1,164 requests in 9 minutes and 1,236 requests in 560 s, no failure in either. In the 560 s run the medians and the 99th percentiles were 83 ms and 92 ms on port 80, 118 ms and 144 ms on port 443 (TLS 1.3, a new handshake each time) and 57 ms and 73 ms on port 8080 (the largest value 259 ms). In the 9-minute run, on a later build, they were 83 ms and 168 ms, 116 ms and 212 ms, and 56 ms and 136 ms. The three ports return the same page.
- **Memory.** The kernel reports 1,960 MiB of frames free before the services start. After the services (nginx, nginx-fast and Dropbear) `/proc/meminfo` shows `MemTotal` 864,500 kB and `MemFree` 480,664 kB (447,896 kB on one first boot). The two views of memory were not reconciled.
- **Network device.** After the loops the console shows `ena: reset ok 2 ms` once (at the start), no `ena: reset reason`, and `rx_drops` and `tx_drops` 0.
- **Scans.** The security group of the runs had four inbound rules. A TCP SYN scan of ports 1 to 65535 (66 s) found 22, 80 and 8080 open and reported 443 as filtered, which was the accept-queue defect fixed in this release; it also found port 113 closed and answers at 2000 and 5060 that the delay (8 ms against 28 ms to the instance) places in the operator's own network device, a point that was not run to the end. A UDP scan of the 200 most common ports got no answer. The image check of the build, and a probe that scans 1,231 forwarded ports on QEMU, find nothing listening beyond 22, 80, 443 and 8080. A complete TCP connect scan of all ports did not finish in 19 minutes from a Mac and was stopped.

### The data volume

The image maps a second volume, `/dev/sdf`, 2 GiB of gp3, made at each launch from the second snapshot of the image. It holds a partition table, a littlefs file system and the SSH host key. The key made at the first boot is saved there (`datakey: host key saved to /data`) and put back at every later boot (`datakey: host key restored from /data`), so the fingerprint is the same after a stop and a start. It was tested over a stop and a start of the same instance, with the same fingerprint on the console and at the SSH client.

- **Cost.** The volume belongs to the account that launches the instance: about 0.19 USD a month in `eu-central-1` (approximate), billed as an EBS volume, and deleted with the instance (`DeleteOnTermination`).
- **Without it.** Launch with the mapping `DeviceName=/dev/sdf,NoDevice=`. Init then leaves the data disk out (`init: left out: datadisk`, `datafs: no disk`), and the host key is new at every boot.
- **Larger.** Give the launch a mapping of the same device with a larger `VolumeSize`, for example `DeviceName=/dev/sdf,Ebs={VolumeSize=4,VolumeType=gp3,DeleteOnTermination=true}`. The volume still comes from the snapshot of the image, and the first boot moves the backup partition table to the end of the disk. The partitions keep their size, so the added space stays unused in this release.
- **A blank volume of your own** attached as `/dev/sdf` is left alone and is unused in this release. The console says `datafs: the disk holds something else, left alone and unused in this release`; nothing writes to it, and the host key is new at every boot. A volume attached after the boot is used from the next boot.
- **A fact about EBS.** On a `t4g.small` a new unencrypted gp3 volume does not read as zeros past its first 4 KiB: from sector 8 on, the bytes are different on each volume and the same on every read. stafeto does not treat such a volume as blank, so the volume of the image comes with its table and its file system already made (`cargo xtask data-image` makes them offline).
- **littlefs** 2.11.3 (BSD-3-Clause) is vendored unchanged in `third-party/littlefs`; its licence is `third-party/littlefs/LICENSE.md` and its `README.md` records the tag and the checksums.

## Highlights

- **The try-out image for AWS.** SSH with the key pair of the instance, nginx, `nginx-fast` and `pkg` as described above. The ENA path of `netd` now serves the consumers of the network switch, so `nginx-fast` runs on EC2 (the 0.4.0 image refused it). `cargo xtask aws boot --try` launches an instance for a session with a key pair, a security group open to the operator's own /32 on 22, 80, 443 and 8080, and a public address, and `tools/aws/try-check.sh` lists the one-hour check.
- **Data volume.** The NVMe disk service (`nvme-blk`) over the EBS volume, the file service `datafs` over littlefs with a GPT, and `datakey` that keeps the SSH host key. Power-cut probes in the host tests stop the workload at every sector with four behaviours of the write cache.
- **The clock on EC2.** The EFI loader reads the time of the firmware (UEFI `GetTime`) before it leaves the boot services and writes it into the boot image, where the clock service reads it. Without a clock the image started at 2026-01-01 and `pkg update` refused every certificate. The firmware of the Nitro instances answers `GetTime`: the clock of the instance and of the operator's machine agreed within 1 s, and `pkg update` works at the first boot.
- **Accept queue of `netd`.** Defects that running on EC2 and port scans showed:
  - A queue socket that the peer resets after the handshake and before `accept` went to CLOSED and kept its place for ever. A SYN with no room now replaces the closed sockets of the queue and of its group, a bounded number per SYN. With four workers of 16 places each, 64 such connections leave a listener with no place; the probe that reproduces it needed the fix to pass.
  - Half-open entries (a SYN with no ACK) stayed for ever. They end after 30 s, and an established connection that sends nothing ends after 120 s; a SYN with no room rebuilds the oldest half-open entry and never an established connection.
  - A queue socket that an RST sends back from SYN-RECEIVED to LISTEN kept the key of its old connection, and the next SYN that took it was answered with an RST at its first ACK. A SYN scan leaves such sockets on every probe, so the first request after a scan failed with "Connection reset by peer". The key is now replaced (counter `key_stale`). On a `t4g.small`, the first requests after a scan (one request to each of 443, 80 and 8080 and one new SSH login) failed in 9 of 10 rounds of SYN scans on `main` at commit 8a6c0f87 (ports 1 to 1,024 five times, and the four ports twenty times in a round, five rounds), and in 0 of 22 rounds with the fix (SYN, TCP connect and UDP scans, 66 first requests and 22 new SSH logins). An SSH session that was open during the scans survived all of them in both runs.
  - A closed socket of a queue keeps its place until it is rebuilt; a frame for such a socket now schedules the rebuild in the idle step, in parts of at most 4 sockets.
  - The counters of the queues (`syn_dropped`, `queue_reaped`, `embryo_recycled`, `key_stale`, the sockets in use, the demux entries and the numbers of each listener) are written on the console of every build, about 30 s after the first request of a boot and then at most every 30 s while one changes.
- **Watchdog of `init`.** A second expiry of a service deadline that arrives late no longer confirms the silence of the service: a late expiry shows that the machine lost time, so the service gets the confirmation period again, up to three late expiries in a row, after which the silence is confirmed. This ended a flicker where a loaded host killed a healthy entropy service.
- **Smaller fixes.** FIFO opens: a signal that interrupted the cleanup of an open leaked a ticket, the leaks filled the table of open FIFOs and new opens were refused with `EAGAIN`; the calls that carry a capability and the whole cleanup now run with signals masked, and pipe errors map to their own codes. An armed interval timer read back with `getitimer` right after `setitimer` could return 0 when its deadline had passed before the helper thread ran; it no longer does. A wait on a set of events (`epoll`, `poll`, `select`) is parked until the steps of sending, receiving and waking have run, so it never reports before the data of a send. `netd` gives way to a request by time, so a stream of datagrams no longer keeps a new process from starting (over 120 s on QEMU with `-icount` before). The steps of a service are judged less the charge of their preemptions. `object_info(MEMORY)` returns the reference count of the object in a register that was free, with no change of the call shape, and the compositor and the display driver use it to refuse a first-revision open while a former client holds the buffer.
- **Graphics.** A composition service (`compositor`) is the one client of the display driver; Doom and the test pattern reach the screen through it, and a program of the first revision gets a window over the whole screen with no rebuild. The preview status of 0.5.0 stays.
- **Service budgets.** See below.

## Service budgets

0.5.1 keeps the budgets of 0.5.0: the network service and the RAM file, pipe and terminal services take at most C of each T from the levels 33 and above and work at level 32 once their budget is spent. It adds three parts:

- The waiters of a lock are told in the request that releases it and in the notice of a departure, at most 2 per request or notice, and the rest in the idle work of the service, so a long queue of waiters never makes a step of the RAM file service longer than its bound of 18,369 ticks.
- The page charge of a detached chain goes when the chain is retired, and the pages wait on the retired list until the maintenance moves them to the free list.
- The gate `service-budget` of `ci` takes every term from the code constants or from the control phase and checks the account of each `serve` budget (the time charged is at most ceil(P / T) times C plus one overrun, and at least C). The group `budgets` of `ci` runs it with the break images that the gate must reject. The share of the victim, a process at a level below the budgets, is printed against its bound and does not fail the gate yet (see the limits).

The 0.5.0 notes planned a service that works at level 1 once its budget is spent. That variant needs kernel support for requests that run on the client's loan with a floor of 1, and for the own work of a service under a budget reserved for it. It comes in a later release, together with a share guarantee for the levels at or below 32.

## Netd step bound

The bound of every step of `netd` is 18,369 ticks under `-icount`, and the target of the code is 16,500 ticks: the worst case of each kind of step, built from measured constants, sums to 16,500 or less, and `ci` warns above it and fails above the bound. A call of LISTEN used to build up to 16 queue sockets in one step (17,376 ticks in the longest run of `posix-net steps`); it now builds at most 4 and tops the queue up in the idle step, and the longest step of that probe is 13,718 ticks. The step that a SYN takes, with the frame, a rebuild of up to 4 sockets and a recycle, is held to the target by the same rule. The prices of a received frame vary by up to 1,000 ticks between runs of one build, which the margin covers.

## Limits

- `aws ec2 reboot-instances` is ignored by the image, and a stop becomes a forced stop after a few minutes: EC2 signals both through ACPI and the image does not handle that yet (issue #435). A stop and a start work; a plain reboot was not tested.
- POSIX programs do not see `/data` yet. Only `datakey` uses the data volume in this release; a route from POSIX programs to `datafs` is planned for 0.6.0.
- A blank volume of your own attached as `/dev/sdf` is left alone and unused. A manual command to turn it into a data volume is not built (issue #434).
- The network stack has no SYN cookies. The accept queue of a listener is bounded (16 places per worker in the tested nginx setup), half-open entries age out after 30 s and idle established ones after 120 s, so a flood of connection attempts that fills a listener keeps new clients out of it until entries age out or are recycled. The rate at which this starts was not measured.
- Files and installed packages are gone after a reboot: the file system and the package store live in memory. Only the SSH host key persists, and only with the data volume. Without it the host key changes at every boot, and the SSH client warns about it.
- `htop` needs `TERM=vt100`.
- A request that arrives right after a SYN scan may wait for a retransmission of its SYN. In the check of the release commit on a `t4g.small` (24 rounds of SYN scans, each followed by one request to port 80 and one to port 443) none of the 48 requests failed and 4, all to port 80, took between 1.08 s and 2.09 s; no packet capture was taken, so the cause is inferred from the times alone. After a UDP scan in the same check, 20 requests to port 80 took 79 ms to 111 ms.
- One request after a UDP scan took 1.2 s on port 80 in a run of 22 scan rounds; the packet capture shows the first data segment of the client waiting for three retransmissions before the instance acknowledged it, with no reset and no change of the counters. The cause is unknown.
- The victim share of the starvation gate for the budgets exceeds the terms that explain it under the 0.5.0 budgets (about 272 microseconds for the RAM file service and 326 for the terminal service per 10 ms), and the gate prints it without failing (issue #430).
- The ENA driver uses one queue pair, and the Low Latency Queue mode is not implemented. Only the instance type `t4g.small` and the region `eu-central-1` are tested.
- Apple VZ gives the kernel no port: a kernel panic there shows nothing and powers the machine off.
- SMP runs on up to 8 CPUs (QEMU, HVF and VZ are tested with 4); the bounds of a real-time analysis on several CPUs still wait for a board.
- `fork` copies everything the layer maps, with no copy on write.
- The network is IPv4. `wget` checks no certificate and speaks TLS 1.2 only.
- Graphics is a preview with one full-screen program, and there is no sound yet.
- Nine POSIX utilities wait for services of their own: `at`, `batch`, `lp`, `mailx`, `locale`, `localedef`, `gettext`, `ngettext` and `msgfmt`.
- The system is experimental. The landing page of the AWS image says so and warns that nothing secret belongs on it.
- Interfaces may still change inside 0.x. The series 0.5 is frozen in `packages/abi.txt`.

## Compatibility

The ABI of the series 0.5 is frozen and does not change: `cargo xtask abi --check` reports `series 0.5 frozen, no change` for each change of this release, and a package built for 0.5.0 runs on 0.5.1. The new services speak new protocols (`proto/data`, `proto/comp`, the revision 2 of `proto/gpu`) that `libc.so` does not use; they are additive.

For people who build images:

- `cargo xtask data-image <path> [--size 2G]` makes the data volume file offline; `cargo xtask aws image` uploads it as a second snapshot and registers `/dev/sdf` from it. The command `aws boot --no-data-volume` maps the device to `NoDevice`, and `aws boot --try` is the try-out launch described above.
- `boot-aws.img` always carries `switch 8` and `flows 16384` in `/etc/netd.conf`; the option `aws image --switch` is gone. The image is built from the base, network and F-Stack packages (15 packages with files).
- The group `budgets` of `ci` is new (`service-budget`, `budget-breaks`), and `net-try` boots the try-out image on QEMU with an NVMe data volume.
- The C parts of littlefs are archived with the `llvm-ar` of the Rust toolchain, which fixes the link of the data services on macOS.
